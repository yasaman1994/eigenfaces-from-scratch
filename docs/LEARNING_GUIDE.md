### جداسازی ۸/۲ برای هر هویت

برای هر شخص، اندیس‌های همان شخص را با مولد تصادفی NumPy و seed ثابت `42` جابه‌جا می‌کنیم؛ ۸ مورد train و ۲ مورد test می‌شوند.

```python
rng = np.random.default_rng(42)

for person in np.unique(labels):
    person_indices = np.where(labels == person)[0]
    shuffled_indices = rng.permutation(person_indices)
    train_indices.extend(shuffled_indices[:8])
    test_indices.extend(shuffled_indices[8:])
```

**چرا؟**

- تعداد نمونه هر هویت دقیقاً حفظ می‌شود؛
- انتخاب فقط بر اساس ترتیب اولیه فایل نیست؛
- seed ثابت باعث می‌شود تمام اعضا دقیقاً یک نتیجه بگیرند.

**جایگزین:** `train_test_split(..., stratify=labels)` نیز از نظر فنی مناسب است، ولی برای هدف آموزشی ترجیح می‌دهیم خود منطق جداسازی را با NumPy ببینیم.

**محدودیت:** نتیجه فقط مربوط به یک split است. اگر زمان داشتیم، پایداری نتیجه را روی چند seed بررسی می‌کردیم؛ اما نتیجه نهایی هر seed نباید برای دست‌کاری و بهترکردن دلخواه گزارش استفاده شود.

**آزمون صحت:**

```python
assert X_train.shape[0] == 320
assert X_test.shape[0] == 80
assert np.all(np.bincount(y_train) == 8)
assert np.all(np.bincount(y_test) == 2)
assert len(np.intersect1d(train_indices, test_indices)) == 0
```

### زنجیره پنج فرمول اصلی PCA در پروژه

این پنج خط، مسیر ریاضی نوت‌بوک را از داده train تا بازسازی خلاصه می‌کنند. توضیح و کنترل هر خط در بخش‌های بعدی آمده است.

**۱. محاسبه میانگین train و مرکزسازی**

```text
mean_face = sum of train images / n
X_train_centered = X_train - mean_face
X_test_centered  = X_test  - mean_face
```

در این پروژه `n = 320` است و برای test نیز همان میانگین train استفاده می‌شود.

**۲. ساخت ماتریس Gram از داده واقعی train**

```text
G = (X_train_centered @ X_train_centered.T) / (n - 1)
```

پس مخرج در پروژه ما `319` است و `G.shape = (320, 320)` می‌شود.

**۳. محاسبه جهت‌های ویژه و تبدیل آن‌ها به eigenface**

```text
G @ v = eigenvalue * v
u = X_train_centered.T @ v
u = u / norm(u)
```

بردار `v` در فضای ۳۲۰ نمونه قرار دارد؛ با ضرب در ترانهاده داده، بردار `u` به فضای ۴۰۹۶ پیکسل می‌رود و پس از نرمال‌سازی یک eigenface می‌شود.

**۴. projection یا فشرده‌سازی با اولین `k` مؤلفه**

```text
Z = X_centered @ U_k
```

در اینجا `U_k.shape = (4096, k)` است؛ بنابراین هر تصویر ۴۰۹۶بعدی به یک کد `k`بعدی تبدیل می‌شود.

**۵. reconstruction یا بازسازی تصویر**

```text
X_reconstructed = Z @ U_k.T + mean_face
```

ابتدا از کد کم‌بعد به فضای پیکسل برمی‌گردیم و سپس چهره میانگین را اضافه می‌کنیم. بعد از این پنج مرحله، MSE کیفیت بازسازی را می‌سنجد و 1-NN روی کدهای `Z` هویت را پیش‌بینی می‌کند.

### واریانس نمونه و تقسیم بر `n-1`

```text
Var(x) = sum((x[i] - mean(x))²) / (n - 1)
```

و برای کل ماتریس مرکز‌شده:

```text
C = (X_centered.T @ X_centered) / (n - 1)
```

در این فرمول، درایه‌های قطر `C` واریانس هر پیکسل و درایه‌های خارج از قطر کوواریانس میان جفت پیکسل‌ها هستند. بنابراین ساخت همین ماتریس، محاسبه هم‌زمان واریانس و کوواریانس روی داده‌های واقعی است.

**چرا `n-1`؟**

چون mean را از همین نمونه‌ها برآورد کرده‌ایم، covariance نمونه معمولاً با درجه آزادی `n-1` تعریف می‌شود.

**نکته مهم:** اگر همه‌جا به‌صورت سازگار بر `n` تقسیم کنیم، جهت eigenvectorها تغییر نمی‌کند و فقط eigenvalueها مقیاس می‌خورند. ما `n-1` را انتخاب کرده‌ایم چون با تعریف sample covariance و صورت پروژه سازگارتر است.

### چرا مثال‌های عددی ساختگی را از نوت‌بوک حذف کردیم؟

برای یادگیری اولیه می‌توان واریانس و کوواریانس را روی آرایه‌هایی مانند `[1, 2, 3, 4, 5]` محاسبه کرد؛ اما صورت پروژه چنین مثالی را به‌عنوان خروجی نخواسته است. این مثال‌ها به دیتاست چهره وصل نبودند و مسیر اصلی نوت‌بوک را قطع می‌کردند. به همین دلیل، تعریف و دلیل فرمول در این راهنمای آموزشی نگه داشته شد و نوت‌بوک فقط محاسبه واقعی روی `X_train_centered` را انجام می‌دهد.

هدف حذف ریاضیات نیست؛ هدف این است که هر محاسبه داخل نوت‌بوک مستقیماً به داده و خروجی پروژه مربوط باشد.

### واریانس کل داده واقعی

لازم نیست برای به‌دست‌آوردن مجموع واریانس، ماتریس بزرگ `C` را بسازیم. مجموع واریانس تمام پیکسل‌ها از مجموع مربع تمام درایه‌های داده مرکز‌شده به دست می‌آید:

```text
total_variance = sum(X_centered[i, j]²) / (n - 1)
```

پیاده‌سازی استفاده‌شده در نوت‌بوک:

```python
total_variance = np.sum(X_train_centered ** 2) / (n_train - 1)
```

از نظر ماتریسی، این مقدار با trace ماتریس covariance برابر است:

```text
total_variance = trace(C)
```

**آزمون نظری در صورت ساختن covariance:** قطر covariance باید برابر واریانس ستون‌ها باشد.

```python
assert np.allclose(np.diag(C), X_train_centered.var(axis=0, ddof=1))
```

ما این تست را داخل نوت‌بوک اجرا نمی‌کنیم، چون به ساخت ماتریس `4096×4096` نیاز دارد و هدف استفاده از Gram matrix، اجتناب از همین محاسبه بزرگ است.

### استفاده از Gram matrix به‌جای covariance بزرگ

### آیا صورت پروژه استفاده از Gram matrix را گفته است؟

بله. در صفحه ۳ فایل `Math-Project-Kickoff.pdf`، گام ۵ مسیر الزامی پروژه می‌گوید ماتریس covariance **یا** Gram matrix را بسازید، تجزیه ویژه را انجام دهید و جهت‌ها را نزولی مرتب کنید. پس هر دو مسیر مجازند.

در صفحه ۱۰ فایل `Math-Project-Kickoff-Eigenfaces-Rahnema-College.pdf` نیز روش مناسب برای حالت `d >> n` توضیح داده شده است: مسئله ویژه کوچک‌تر `n×n` را روی Gram matrix داده train حل کنید و سپس جهت‌ها را به فضای اصلی برگردانید. در همان اسلاید به استفاده از `eigh` روی Gram matrix اشاره شده است.

بنابراین Gram matrix میان‌بری خارج از پروژه نیست؛ یکی از دو مسیر رسمی و پیشنهادی پروژه است.

### چرا برای داده ما انتخاب مناسبی است؟

داده مرکز‌شده train این شکل را دارد:

```text
X_train_centered.shape = (320, 4096)
```

یعنی:

```text
n = 320     number of train images
d = 4096    number of pixels in each image
```

در این پروژه تعداد ویژگی‌ها بسیار بیشتر از تعداد نمونه‌هاست:

```text
4096 >> 320
```

اگر covariance پیکسل‌ها را بسازیم:

```text
C = (X_centered.T @ X_centered) / (n - 1)
C.shape = (4096, 4096)
```

این ماتریس `16,777,216` درایه دارد. اما Gram matrix چنین است:

```text
G = (X_centered @ X_centered.T) / (n - 1)
G.shape = (320, 320)
```

Gram matrix فقط `102,400` درایه دارد؛ یعنی تعداد درایه‌های آن حدود ۱۶۴ برابر کمتر است. بنابراین نگهداری ماتریس و اجرای eigendecomposition روی آن بسیار سبک‌تر می‌شود.

### آیا Gram matrix همان covariance matrix است؟

خیر. این دو شکل و معنای متفاوتی دارند:

- `C` ارتباط میان ویژگی‌ها یا پیکسل‌ها را نشان می‌دهد و شکل آن `d×d` است.
- `G` ارتباط میان نمونه‌های train را نشان می‌دهد و شکل آن `n×n` است.

پس نباید در توضیح یا ارائه، Gram matrix را «همان covariance پیکسل‌ها» بنامیم. نکته درست این است که این دو ماتریس، eigenvalueهای غیرصفر یکسان و جهت‌های اصلی متناظر دارند.

### چرا نتیجه غیرصفر PCA یکسان می‌ماند؟

اگر:

```text
G @ v = lambda * v
```

اکنون دو طرف معادله را در ترانهاده داده‌های مرکز‌شده ضرب می‌کنیم:

```text
C @ (X_centered.T @ v) = lambda * (X_centered.T @ v)
```

پس بردار زیر، یک بردار ویژه از ماتریس کوواریانس بزرگ است:

```text
X_centered.T @ v
```

مقدار ویژه آن نیز با مقدار ویژه غیرصفر ماتریس گرام برابر است. در پایان، طول این بردار را برابر یک می‌کنیم.

کد پروژه همین تبدیل را انجام می‌دهد:

```python
eigenfaces = X_train_centered.T @ eigenvectors

lengths = np.sqrt(np.sum(eigenfaces ** 2, axis=0))
eigenfaces = eigenfaces / lengths
```

پس ابتدا مسئله کوچک‌تر را حل می‌کنیم و سپس بردارهای ویژه را به فضای ۴۰۹۶ پیکسلی برمی‌گردانیم.

یک کنترل مستقیم روی داده واقعی این است که مجموع eigenvalueهای غیرصفر Gram با واریانس کل داده برابر باشد:

```python
variance_is_preserved = np.allclose(
    np.sum(eigenvalues),
    total_variance,
)
```

دلیل این برابری آن است که مجموع eigenvalueهای یک ماتریس متقارن با trace آن برابر است و trace ماتریس Gram نیز با trace ماتریس covariance برابر می‌شود. در این پروژه، این کنترل نشان می‌دهد واریانس موجود در داده train هنگام رفتن از مسیر covariance به مسیر Gram گم نشده است.

**چرا حداکثر ۳۱۹ مؤلفه مفید داریم؟**

مرکزسازی یک وابستگی خطی ایجاد می‌کند؛ جمع ردیف‌های داده مرکز‌شده صفر است. بنابراین rank حداکثر `n_train - 1 = 319` است.

Gram matrix نیز در اجرای فعلی دقیقاً ۳۱۹ eigenvalue مفید تولید کرده است. بنابراین استفاده از ماتریس کوچک‌تر باعث حذف هیچ جهت PCA غیرصفری نشده است.

### آیا Gram matrix همیشه انتخاب بهتری است؟

خیر. انتخاب به اندازه داده بستگی دارد:

```text
اگر d >> n باشد: Gram matrix معمولاً کوچک‌تر است.
اگر n >> d باشد: covariance matrix ممکن است کوچک‌تر باشد.
```

برای این پروژه `d = 4096` و `n = 320` است؛ بنابراین Gram matrix انتخاب منطقی‌تری است.

### جمله کوتاه برای ارائه

> چون هر تصویر ۴۰۹۶ ویژگی دارد ولی فقط ۳۲۰ تصویر آموزشی داریم، به‌جای حل مسئله بزرگ `4096×4096`، مسئله کوچک‌تر `320×320` را حل می‌کنیم و بردارها را دوباره به فضای تصویر برمی‌گردانیم.

### استفاده از `np.linalg.eigh`

Gram و covariance ماتریس‌های حقیقی متقارن‌اند. `eigh` مخصوص ماتریس‌های متقارن است و eigenvalueهای حقیقی و eigenvectorهای نرمال‌شده برمی‌گرداند.

**چرا `eig` نه؟**

`eig` برای ماتریس عمومی است و از ساختار متقارن مسئله استفاده نمی‌کند. برای این مسئله `eigh` انتخاب روشن‌تر و مناسب‌تری است.

**نکته خروجی:** `eigh` eigenvalueها را صعودی می‌دهد؛ PCA به ترتیب نزولی نیاز دارد.

```python
order = np.argsort(eigenvalues)[::-1]
eigenvalues = eigenvalues[order]
eigenvectors = eigenvectors[:, order]
```

**آزمون‌های صحت:**

```python
assert np.allclose(L, L.T)
assert np.all(np.diff(eigenvalues) <= 0)
assert np.allclose(
    eigenfaces.T @ eigenfaces,
    np.eye(eigenfaces.shape[1]),
    atol=1e-10,
)
```

ممکن است چند eigenvalue منفی بسیار کوچک در حد خطای floating-point دیده شود. آن‌ها و مؤلفه‌های تقریباً صفر با threshold نسبی حذف می‌شوند، نه با یک عدد بزرگ دلخواه.

### projection به فضای کم‌بعد

اگر `U_k` شامل اولین `k` eigenface باشد:

```text
Z = X_centered @ U_k
```

ابعاد:

```text
X_c: (n, 4096)
U_k: (4096, k)
Z:   (n, k)
```

هر ردیف `Z` کد فشرده یک چهره است.

**آزمون صحت:**

```python
assert train_codes.shape == (320, k)
assert test_codes.shape == (80, k)
```

### reconstruction

```text
X_reconstructed = Z @ U_k.T + mean_face
```

ابتدا از فضای `k`بعدی به فضای ۴۰۹۶بعدی برمی‌گردیم و سپس mean face را اضافه می‌کنیم.

**اشتباه رایج:** فراموش‌کردن اضافه‌کردن mean باعث می‌شود خروجی فقط deviation از میانگین باشد، نه تصویر بازسازی‌شده.

**آزمون صحت:** برای eigenfaceهای مرتب‌شده، با افزایش `k` خطای بازسازی نباید زیاد شود؛ اختلاف بسیار کوچک در حد خطای اعشاری قابل‌قبول است.

### استفاده از MSE برای خطای بازسازی

```text
MSE = sum((X - X_reconstructed)²) / (n * d)
```

**چرا؟**

MSE ساده، قابل‌توضیح و مستقیماً با هدف کمینه‌سازی خطای مربعی PCA هماهنگ است.

**محدودیت:** MSE الزاماً با کیفیت ادراکی تصویر برابر نیست؛ به همین علت مقایسه بصری نیز گزارش می‌کنیم.

### nearest neighbor از صفر

برای هر کد test، فاصله یا شباهت آن را با تمام کدهای train حساب می‌کنیم و label نزدیک‌ترین نمونه را برمی‌گردانیم. این روش هیچ پارامتر یادگرفتنی اضافه‌ای ندارد.

**Euclidean distance:**

```text
d(a, b) = sqrt(sum((a[j] - b[j])²))
```

کمترین فاصله انتخاب می‌شود. برای مقایسه همسایه‌ها می‌توان ریشه دوم را حذف کرد، چون ترتیب فاصله‌ها تغییر نمی‌کند.

**Cosine similarity:**

```text
s(a, b) = (a.T @ b) / (norm(a) * norm(b))
```

بیشترین شباهت انتخاب می‌شود. تقسیم بر صفر باید با بررسی norm یا یک epsilon بسیار کوچک کنترل شود.

### مقایسه Euclidean و Cosine بدون whitening

در فضای PCA، واریانس مؤلفه `j` برابر eigenvalue همان مؤلفه است. بنابراین مؤلفه‌های ابتدایی معمولاً مقیاس بزرگ‌تری دارند.

- Euclidean به اختلاف عددی مختصات حساس است؛ مؤلفه‌های با تغییرات بزرگ‌تر می‌توانند سهم بیشتری داشته باشند.
- Cosine طول کل بردار را حذف و بیشتر جهت دو بردار را مقایسه می‌کند.
- Cosine به‌تنهایی تک‌تک مؤلفه‌ها را هم‌مقیاس یا whiten نمی‌کند.

برای مقایسه اصلی، هر دو معیار باید دقیقاً روی یک `train_codes` و `test_codes` و بدون preprocessing متفاوت اجرا شوند؛ وگرنه فقط معیار فاصله را مقایسه نکرده‌ایم.

**آزمایش اختیاری:** whitening با تقسیم هر مؤلفه بر `sqrt(eigenvalue[j])` موضوع جالبی است، اما سؤال متفاوتی می‌سازد. اگر انجام شود باید جدا و با برچسب آزمایش تکمیلی گزارش شود.

### انتخاب مقدارهای `k`

مقادیر اصلی قبل از دیدن accuracy آزمون تعیین می‌شوند. برای نمودار دقیق‌تر می‌توان مجموعه زیر را نیز اجرا کرد:

```text
1, 5, 10, 20, 50, 100, 150, 250
```

**چرا؟**

اگر بارها با test امتحان کنیم و فقط بهترین `k` را گزارش کنیم، test عملاً به validation تبدیل می‌شود و accuracy نهایی خوش‌بینانه خواهد بود.

در این پروژه سه مقدار الزامی را کامل گزارش می‌کنیم و از پنهان‌کردن نتایج ضعیف خودداری می‌کنیم.

### مقایسه کوتاه با SVD

برای داده مرکز‌شده:

```text
X_centered = Q @ Sigma @ V.T
```

ردیف‌های `V^T` جهت‌های اصلی در فضای پیکسل‌اند و رابطه eigenvalueها چنین است:

```text
eigenvalue[j] = singular_value[j]² / (n - 1)
```

**چرا بردارها را پیکسل‌به‌پیکسل مقایسه نمی‌کنیم؟**

علامت eigenvector دلخواه است؛ `u` و `-u` یک جهت را نمایش می‌دهند. در eigenvalueهای تکراری حتی پایه‌های متفاوت می‌توانند همان زیرفضا را بسازند. معیار بهتر، reconstruction error یا فاصله بین projection matrixهای دو زیرفضاست.

### accuracy، موفقیت و شکست

```text
Accuracy = correct_predictions / number_of_test_samples
```

فقط accuracy کافی نیست. باید حداقل این موارد را ببینیم:

- یک نمونه درست و نزدیک‌ترین تصویر train آن؛
- یک نمونه اشتباه و نزدیک‌ترین تصویر train آن؛
- چند نمونه که Euclidean و Cosine همسایه متفاوت انتخاب کرده‌اند؛
- توضیح محتاطانه درباره نور، حالت چهره، عینک یا زاویه.

نباید از یک نمونه، قانون کلی درباره علت شکست استخراج کنیم؛ توضیح ما یک احتمال مشاهده‌شده است.

### استفاده از بخش‌های مناسب کد اولیه صبا

از کد اولیه صبا، منطق ساده نزدیک‌ترین همسایه Euclidean، شباهت Cosine و نمایش نمونه‌هایی با همسایه متفاوت استفاده شد. این بخش‌ها با قرارداد نهایی پروژه بازنویسی شدند.

قسمت‌های زیر از نسخه اولیه وارد پروژه نشدند:

- split برابر ۷۰/۳۰، چون صورت پروژه دقیقاً ۸ تصویر train و ۲ تصویر test برای هر هویت می‌خواهد؛
- `train_test_split`، چون split ساده NumPy پروژه روشن‌تر و مطابق تصمیم تیم است؛
- `np.linalg.eig`، چون برای Gram متقارن `np.linalg.eigh` مناسب‌تر است؛
- انتخاب بهترین `k` با نگاه‌کردن به test، چون باعث استفاده نادرست از داده آزمون برای تصمیم‌گیری می‌شود؛
- بخش مأموریت Team 3، چون خروجی اختصاصی تیم ۴ نیست.

به این ترتیب ایده و مشارکت صبا حفظ شده، ولی کل کد با یک split، یک نام‌گذاری و یک روش ریاضی سازگار اجرا می‌شود.
